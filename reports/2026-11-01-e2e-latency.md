# End-to-end latency: Syphon publish → on-screen draw (macOS, 2026-11-01)

Follow-up to `2026-11-01-hot-path-baseline.md`. That report covered the path up to the main-process JS push callback. This one measures every stage after it, through to the renderer draw, and checks whether the `sendSharedTexture` round trip limits delivered fps.

## Method

Bench: `packages/renderer/bench/e2e-latency/` (`main.mjs`, `preload.cjs`, `index.html`, `producer-worker.cjs`, `run-matrix.mjs`, `summarize.mjs`).

```bash
# one configuration
PIPE=A DRAW=2d W=3840 H=2160 N=16 packages/example/node_modules/.bin/electron packages/renderer/bench/e2e-latency/main.mjs
# full matrix (one Electron process per config, pkill after each) + tables
node packages/renderer/bench/e2e-latency/run-matrix.mjs results.jsonl
node packages/renderer/bench/e2e-latency/summarize.mjs results.jsonl
```

Stamps are `performance.timeOrigin + performance.now()` in every thread and process:

| Stamp | Where |
| --- | --- |
| T_pub | producer worker (`worker_threads`, `TextureSender.sendRgbaBuffer` at 60 Hz), right after the call returns. Same definition as the hot-path report |
| T_cb | entry of the `TextureReceiver.onSharedTexture` callback (main) |
| T_deq | start of delivery: equals T_cb unless the frame waited as the latest-wins pending frame |
| T_imp | after `sharedTexture.importSharedTexture()` returns (`closeNativeHandle` runs right after it) |
| T_send | after `sharedTexture.sendSharedTexture()` returns synchronously |
| T_ack | `sendSharedTexture` promise resolved (main) |
| T_rx | entry of the renderer `onFrame` (`installSharedTextureReceiver` + one `consumeSharedTexture` that routes by slot, like `multiviewer.ts`. `getVideoFrame()` has already run) |
| T_draw | after `drawImage` / `queue.submit` returns (CPU side) |
| GPU done | `await device.queue.onSubmittedWorkDone()` (WebGPU only) |
| rAF | rAF callback start that first draws the frame (`DRAW=2d` only) |

- **PIPE=A** is an instrumented replica of `createSharedTextureReceiver` push mode: import → `closeNativeHandle` (success or throw) → `sendSharedTexture(..., slot, deliveryId)` → `imported.release()` in `finally` after the promise settles. Latest-wins applies while a send is in flight: only the newest pending frame is kept and the older handle is closed.
- **PIPE=B** is the real `createSharedTextureReceiver({ mode: "push", extraArgs: [slot, -1] })` from `packages/renderer/dist`. It can only measure the totals.
- **DRAW** variants:
  - `2d` follows `multiviewer.ts`: clone and hold the latest VideoFrame, then `drawImage` every held slot on every rAF.
  - `2d-immediate`: `drawImage` inside `onFrame`.
  - `webgpu`: `importExternalTexture` plus a fullscreen pass inside `onFrame`, awaiting GPU completion.
  - `none` (isolation only): stamp only, no draw.
- **Scale**: W×H 1920×1080 and 3840×2160. N = 1, 4 or 16 receivers on the same Syphon source, each with its own `TextureReceiver` and its own canvas. Canvases are 480×270 backing pixels (multiviewer deck size) in one 1280×760 window. `WINDOWS=1` (one window per receiver) was measured for `A/2d/1080p` only. Extra isolation runs: `DRAW=none` at N=1/16, and an N=8 knee point at 4K.
- **Run length**: warm-up 60 published frames, then 360 published frames recorded (~6 s) per config. Per-stage stats count every delivered frame in the window across all receivers, so N=16 gives ~5700 samples.
- **Main event-loop delay**: `perf_hooks.monitorEventLoopDelay({ resolution: 1 })` over the recording window. Each sample includes the 1 ms sampling period, so ~1.3 ms means ~0.3 ms of real lag.
- **Cell format**: tables give mean / p95 / p99 in ms.

### Caveats

- **Seq approximation (A).** The native callback carries no frame id. A callback is attributed to the seq the producer most recently *started* publishing (an Atomics counter read inside the callback). T_pub is that seq's publish-call end. If the callback for frame k arrives after frame k+1 has started, it is misattributed. That is rare at 60 Hz with 1–4 ms latency, but it shows up as a few negative "native drops" in saturated runs. `pub→cb` can be slightly negative, because Syphon may notify before `sendRgbaBuffer` returns.
- **Latest-pub matching (A vs B).** B cannot carry a seq because `extraArgs` is fixed per receiver. Each renderer arrival is matched to the latest publish that completed before it. A is also reported this way so the two can be compared directly. This under-reports latency whenever latency exceeds one frame period, so the saturated rows are lower bounds.
- **Clocks.** A main↔renderer ping-pong (best of 30, RTT 0.15–0.25 ms) gave offsets of −0.31 to +0.10 ms (not applied). Renderer `performance.now()` granularity is 0.1 ms (Chromium clamp). Renderer sub-ms stages such as draw CPU 0.1 ms and send→T_rx ≈ 0 are therefore at resolution. The one negative mean (send→T_rx −0.08 ms) came from the run with offset −0.31 ms.
- **Display and host.** The window is visible on a 120 Hz ProMotion display (rAF interval 8.3 ms). On a 60 Hz display the rAF wait doubles: uniform in [0, 16.7] ms instead of [0, 8.3] ms. An unrelated Electron app (Genovese dev instance) was running throughout, and runs at saturated configs varied noticeably between repeats (see below).
- **Single run per config** apart from the repeats noted below. Treat differences under ~0.5 ms between rows as noise.

## Environment

Apple M5 Pro, 24 GB, macOS 26.4.1 (25E253). Electron 40.2.1. Native addon built from `main` (ca13d90; `origin/main` e1a5695 differs only by release-please version bumps). core and renderer dist were built from the worktree.

## When does `sendSharedTexture` resolve? (Electron v40.2.1 source)

`lib/browser/api/shared-texture.ts` `sendSharedTexture()`:

1. `imported.subtle.startTransferSharedTexture()`.
2. `invokeInWebFrameMain(frame, IMPORT_SHARED_TEXTURE_TRANSFER_MAIN_TO_RENDERER, transfer, textureId, ...args)`.
3. Awaits the reply, raced against a 1000 ms timeout.
4. `setReleaseSyncToken(syncToken)`, then registers the renderer-frame reference.

`lib/renderer/api/shared-texture.ts`, the handler for that channel:

1. `finishTransferSharedTexture(...)`.
2. `getFrameCreationSyncToken()`.
3. **`event.sender.send(replyChannel, null, syncToken)`**.
4. *Then* `await sharedTextureReceiverCallback(data, ...args)`.

**The promise resolves when the renderer's main thread has run the internal IPC handler and replied with the sync token. That happens before the receiver callback runs, so it does not wait for `onFrame`, `getVideoFrame()` or any draw.** The renderer must:

- have a receiver registered (otherwise the main side times out after 1 s);
- have its main thread free to run the IPC handler.

The renderer's own `imported.release()` is a separate, later `RELEASE_RENDERER_TO_MAIN` invoke. The client defers it by `setTimeout(0)`. It does not gate the main promise.

Consequences, all confirmed by the measurements below:

- `createSharedTextureReceiver`'s in-flight gate (`_inFlight` until the promise settles) is bounded by **IPC round trip + renderer main-thread availability**, not by draw cost. Measured T_ack lands 0.03–1.0 ms after T_rx (mean), and send→ack is 0.2–0.4 ms at N ≤ 4.
- There is **no backpressure from the renderer's `onFrame` to main.** An async consumer (WebGPU awaiting GPU completion) can stack unbounded concurrent `onFrame` calls and live VideoFrames. Measured: 93 at N=16 1080p, ~300 at N=16 4K.
- The round trip *does* cap fps when the renderer main thread stalls. In that case the ack waits for the stall (see N=16 4K, `2d-immediate`).

Measured facts:

- With **no draw** (`none`), N=16 4K is healthy: 59 fps delivered, round trip 0.17 ms, main ELD p99 2.1 ms. Transport is therefore not what collapses: 16 native staging copies + 16 imports + 16 IPCs per frame keep up. Its cost appears only as latency, with pub→cb growing from 2.4 ms (N=1) to 4.1 ms (N=16).
- Adding a 480×270 draw per receiver collapses throughput in every draw mode, in both A and B. The renderer's rAF interval rises from 8.3 ms to 21–115 ms. The same 16 draws from a 1080p source are fine (8.3 ms rAF), so the cost scales with **source** pixel count, not destination size.
- In `2d` mode the main→renderer delivery keeps up (59 fps), but the rAF loop only draws 32–47 fps. Frames are replaced in the hold slot before any rAF draws them ("superseded").
- In `2d-immediate`, the renderer main thread stalls for 100–370 ms at a time (rAF max). The renderer IPC handler that replies the sync token cannot run during the stall, so **send→ack grows from 0.3 ms to a 6–28 ms mean and 72–212 ms p95**. Main's latest-wins then drops 70–196 frames per receiver, and delivered fps falls to 25–48. This is the one place where the T_ack round trip caps fps. ack−T_rx stays at 0.8 ms, so the delay sits *before* the renderer handler, not in the reply.
- In `webgpu` the GPU queue backs up (GPU done ~0.4–1 s after receive). Because the ack does not wait for `onFrame`, ~300 `onFrame` calls and their VideoFrames are alive at once. Producer upload p99 also climbs to 77–107 ms and published fps drops to 48–50: the whole GPU is saturated, the producer included.
- Run-to-run variance is large in this regime (2d drawn 32 → 47 fps; 2d-immediate delivered 25 → 48 fps).

## Where the time goes

Ranked for the normal (unsaturated) case. Example: `2d` multiviewer, 1080p, N=1, total pub→draw 5.9 ms mean / 9.7 ms p95.

1. **rAF wait in the hold-latest `2d` pattern: 3.7–5.3 ms mean, p95 7–10 ms, which is 60–75% of publish→draw.** It is uniform over one display refresh (8.3 ms here at 120 Hz, so it would be ~8 ms mean and up to 16.7 ms on 60 Hz). `2d-immediate` and `webgpu`-in-`onFrame` remove it: pub→draw 1.7 ms vs 5.9 ms at 1080p N=1. (Measured.) The frame still reaches the screen only at the next compositor frame, so part of the saving is moved rather than removed (hypothesis; not measured, as there is no presentation timestamp).
2. **T_pub → T_cb (Syphon notify + native GPU staging copy): 1.2 ms at 1080p, 2.4 ms at 4K, rising to 2.6 / 4.1–4.5 ms at N=16.** This is the biggest stage on the transport side, and it grows with N even without drawing (`none`: 2.4 → 4.1 ms at 4K). (Measured.) Each `TextureReceiver` does its own GPU copy of the same source frame, so N receivers on one source mean N identical copies. (Hypothesis for the cause of the N-scaling: GPU queue contention between the per-receiver copies.)
3. **GPU completion of the renderer draw: 1.0 ms (1080p) / 1.7 ms (4K) at N=1, 3–6 ms at N=4–8 4K.** (Measured, WebGPU only. 2d has no completion signal.)
4. Everything on the main thread after the callback is small and flat: import 0.03–0.07 ms, `sendSharedTexture` sync call 0.1–0.14 ms, IPC delivery to `onFrame` 0.1–0.3 ms, round trip 0.2–0.4 ms (≈1 ms at N=16). **The T_ack round trip does not cap fps under normal load:** it is ≤ 1.1 ms mean against a 16.7 ms frame period, and there were zero latest-wins drops. (Measured.)

### Optimization candidates

1. **Fan out one received frame per Syphon source instead of N receivers.** Evidence: at N=16 4K, pub→cb rises 2.4 → 4.1 ms even with no draw. Saturation scales with source resolution × N. Each receiver does its own 4K staging copy and its own import. One `TextureReceiver` + one `importSharedTexture` per source, then `sendSharedTexture` to each target (or one target that draws to N canvases), would remove N−1 GPU copies and imports. Expected gain (hypothesis): pub→cb back near the N=1 value and more GPU headroom for the renderer at 4K × many.
2. **Bound renderer-side work per slot (backpressure or latest-wins in the consumer).** Evidence: the `sendSharedTexture` promise resolves before `onFrame` runs (Electron source + ack−T_rx ≈ 0.1 ms). WebGPU consumers piled up to 93 (1080p N=16) and ~300 (4K N=16) concurrent `onFrame`s and VideoFrames, with GPU-done latency reaching 0.4–1.4 s. Options:
   - skip/close a frame in the client when that slot's previous `onFrame` is still pending;
   - or add a library-level "consumed" ack so main's `_inFlight` covers the draw.

   The second option trades fps for bounded latency, so it should be opt-in.
3. **Draw on arrival (or in a worker / `requestVideoFrameCallback`-like path) instead of hold-and-rAF when latency matters.** Evidence: the rAF wait is the largest single stage (4–5 ms mean here; ~8 ms expected at 60 Hz). Drawing in `onFrame` cut pub→draw from 5.9 to 1.7 ms. Caveat, measured: under 4K × 16 saturation, drawing in `onFrame` was worse for throughput (renderer main-thread stalls delay the IPC ack → 25–48 fps) than the hold-and-rAF pattern, which still received 59 fps. Draw-on-arrival therefore needs candidate 2's per-slot bound to be safe.

Not worth optimizing now: import, the sync send call, and main event-loop load. They total ≤ 0.3 ms per frame per receiver, and main ELD p99 was ≤ 3.8 ms at N=16.

### Open questions (not measured)

- Why a 480×270 draw from a 4K VideoFrame costs enough GPU time to saturate at N=16 (rAF 21–115 ms), while the same draws from 1080p are free. This suggests a full-resolution copy or format conversion per `drawImage` / `importExternalTexture` of a shared-image VideoFrame. Confirming it needs a GPU trace (`chrome://tracing` / Instruments Metal System Trace).
- Presentation latency (draw → photons) is not covered: there is no presentation timestamp in this bench.

## After: fan-out (`forwardFrames`), 2026-11-02

Re-measure for candidate 1 after `SharedTextureReceiverBridge.forwardFrames()` landed (plan `docs/superpowers/plans/2026-11-02-receiver-fan-out.md`, Task 1, uncommitted working tree). One native receiver per source, one import per frame, per-target latest-wins.

### Method delta

- **PIPE=B (before)**: N × `createSharedTextureReceiver({ senderName, target, mode: "push", extraArgs: [slot, -1] })` on the same Syphon source, i.e. N native receivers, N staging copies and N imports per frame. It runs the Task-1 build, where a single `target` is the "primary forward". So B is the N-receivers baseline on the new code, not yesterday's binary.
- **PIPE=F (after)**: one `createSharedTextureReceiver({ senderName, target: <window>, mode: "push", extraArgs: [0, -1] })` plus N−1 `receiver.forwardFrames(<window>.webContents, { extraArgs: [slot, -1], onStatus })`. Canvases, draw modes and renderer stamps are the same as in B (all targets are the one bench window, routed by slot), so the totals compare directly.
- **pub→import replaces pub→cb for B/F.** The real API gives no hook at the native callback, so the bench wraps `electron.sharedTexture.importSharedTexture` (the bridge looks it up at call time) and stamps each call. The import is the first point that can be instrumented after the callback. In A it lands about 0.05–0.1 ms after T_cb. Seq attribution is the same as A (`publishingSeq()` at import time), with the same caveat. The same wrapper counts **imports per published frame**. It is applied to both B and F, so the pair is fair.
- **Matrix**: DRAW `none` / `2d` / `webgpu` × 1080p / 4K × N = 1 / 4 / 16. B and F run back to back for each config, and the order flips every other pair to cancel drift. The 4K N=16 configs ran 3 times each, interleaved. Otherwise the settings match the earlier runs: 60 warm-up frames, 360 recorded frames, 480×270 canvases in one window, 120 Hz display. In tables with repeats, each cell is the median across runs of that run's mean (or p95).
- **Process hygiene**: `run-matrix.mjs` now starts each Electron in its own process group (`detached`) and SIGKILLs only that group after the run. The broad `pkill -f e2e-latency/main.mjs` is gone. Every run reported 0 leftover processes.
- **Load**: the Task-2 marker (`task2-electron-done`, 01:34) was present before the first run, and no example-app Electron was running. An unrelated **Genovese dev Electron** (`.claude/worktrees/issue-306`, pid 92357, `--remote-debugging-port=9222`) ran throughout. It is background load, the same situation as yesterday's runs.

### Measured facts

- **Imports per published frame drop from N to 1** in every F run. In 0 of 27 F runs was there an `"error"` event or an `onStatus` failure, and all N−1 forwards were still `active` when stopped.
- **The N-scaling of publish→callback is gone.** At 4K N=16 without drawing, pub→import is 4.11 ms in B and 2.42 ms in F. F matches N=1 (2.65 / 2.71 ms). pub→T_rx falls from 4.29 to 3.23 ms. The pattern is the same at 1080p N=16 (2.44 → 1.24 ms) and in every N ≥ 4 row. This confirms candidate 1's premise: the extra latency came from the N per-receiver receives.
- **4K × N=16 `webgpu`**: B saturated in all 3 runs (34–53 fps delivered, GPU done 133–380 ms, 272–301 concurrent `onFrame`s, published fps 51–56). F was fully healthy in 2 of 3 runs: 59.3–59.4 fps, GPU done 12.4–12.9 ms, rAF 8.3 ms, max depth 27–29. The other F run (run 34, the first heavy webgpu run) was degraded, though less than any B run: 46.9 fps, GPU done 112 ms, depth 304.
- **4K × N=16 `2d`**: delivery was at 59 fps in both. The rAF loop draws 55.7–57.6 fps in F against 44.0–47.9 in B. Superseded frames fall from 1109–1494 to 160–337, and pub→T_draw from 13.5–14.2 to 10.3–11.7 ms. **The rAF interval is still 17.0–17.5 ms in F, against 8.3 ms when unsaturated.** The renderer still misses every other 120 Hz vsync.
- **Main process**: ELD p99 is lower in F at N=16 in every draw mode (1.73–2.00 vs 2.08–2.45 ms). Main was not the bottleneck before either.
- **No regression on the legacy single-`target` path**: B 4K N=16 `2d` reproduces yesterday's B within run-to-run variance (drawn 44–48 fps vs 39.8, rAF 21–23 vs 25 ms). B and F at N=1 agree within noise in every draw mode.

### Conclusion

| draw mode at 4K × N=16 | verdict |
| --- | --- |
| `none` (transport only) | **Resolved.** Imports 16 → 1, publish→import back to the N=1 value. |
| `webgpu` | **Largely resolved, not yet reliably.** 2 of 3 F runs ran at the full 59 fps with ~13 ms GPU done; 1 of 3 still degraded (47 fps, 112 ms). B saturated 3 of 3. |
| `2d` (hold + rAF, multiviewer pattern) | **Partially resolved.** Drawn fps 45 → 57 and superseded frames down by ~6×, but the rAF interval is still ~17 ms, so the renderer has no headroom left. |

Hypotheses (not measured):

- Fan-out removed N−1 4K staging copies and imports. That freed GPU time, which is the likely reason the webgpu queue no longer backs up in most runs.
- The remaining `2d` cost is in the renderer: 16 `drawImage` calls per rAF, each from a 4K shared-image VideoFrame (see the open question above). Fan-out does not change that work. The fix there is candidate 2 (bound per-slot renderer work) or candidate 3 (draw on arrival), or drawing a downscaled copy once per source instead of once per slot. A GPU trace is still needed to confirm.
- The one degraded F webgpu run is consistent with the system being at the edge: the 4K producer upload and the Genovese dev app share the GPU. With 3 runs, this is not separable from noise.

### Incident: one Electron SIGSEGV (producer teardown)

1 of 62 Electron runs (48 matrix + 2 smoke + 12 re-checks), `F/none/4K/N=1` run 7, crashed with no RESULT. The macOS report `~/Library/Logs/DiagnosticReports/Electron-2026-11-02-013818.ips` shows:

- `EXC_BAD_ACCESS` at 0x200 on `com.Metal.CompletionQueueDispatch` in `-[SyphonServerConnectionManager publishNewFrame]`, called from a Metal command-buffer completion handler. That is the **producer** side (the bench's `TextureSender` in a worker thread), not the receive/forward path.
- Capture time is 8.1 s after launch, and a normal run takes ~8.7 s, so the crash happened during teardown.
- No producer worker thread was alive.

Re-running the config 6 × F and 6 × B (interleaved) did not reproduce it. Yesterday's `Electron-2026-11-01-195019.ips` is a different crash (an `abort` on the main thread).

Hypothesis: `producer-worker.cjs` never disposes its `TextureSender`. `worker.terminate()` tears the Syphon server down while a Metal completion handler is still running and calls `publishNewFrame`. That would be a teardown race in the bench producer, or in the native sender's dispose path. It should be followed up separately and is not related to `forwardFrames`.
